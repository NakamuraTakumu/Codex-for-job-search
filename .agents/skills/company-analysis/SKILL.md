# 目的
- **用途**: 親エージェントが会社分析を子エージェントへ委譲するときに使う。
- **子の出力**: Markdown ではなく YAML を返す。
- **親の担当**: Markdown への描画、ファイル保存、最終成果物の生成は親エージェントまたは script が担当する。
- **保存の禁止**: 子は final artifact を保存・更新・生成してはいけない。親が `tmp/company_analysis/subagent_outputs/<run_slug>/<uuid>.yaml` 形式の handoff path を明示した場合だけ、返却する YAML と同一内容をその 1 ファイルへ保存してよい。子は handoff path を生成・変更せず、保存先の決定、Markdown rendering、final artifact の作成は親だけが行う。
- **run_metadata**: この skill が返す YAML には `run_metadata` を含めない。`run_metadata` は親 runner が受理時に追加する。

# 想定読者
- **人物像**: 上位国立大学の研究志向な博士課程学生、またはそれに近いプロフィールの人物を既定とする。
- **居住地**: 仙台を既定とする。
- **関心**: 機械学習、数学や抽象理論、形式化、プログラミング言語理論、ソフトウェア工学、アルゴリズム実装、GPU や型システムのような計算機システム実装、および研究成果をソフトウェアや社会実装へつなぐことにある。
- **優先する評価**: 単なるトピックの一致だけを高く評価せず、博士の専門性が採用制度上どう評価されるかを優先する。

# 中核原則
- **評価対象**: 会社プロフィールとしてではなく、「働く場」として評価する。
- **分離**: 事実と評価を分ける。
- **優先順位**: 速さよりも、評価対象に対する網羅性と、公式 / 非公式の明確な分離を優先する。時間を使ってよく、穴を急いで埋めてはいけない。
- **欠損の扱い**: 重要な欠損が見つかったとき、単に `unconfirmed` と書いて済ませず、追加調査の優先対象として扱う。
- **ローカル汚染の禁止**: リポジトリ内の `document/`、`report/`、archive output、既存の会社分析、review note、他 agent output を読んではいけない。過去のローカル分析を引き継がず、公開情報を直接調べる。
- **template の早期参照禁止**: `references/output-contract.md` や `assets/yaml_output_template.yaml` を、出力 schema を先に固定するために早い段階で開いてはいけない。最終出力制約を見る前に、まず調査と証拠の骨格を固める。
- **情報源の広さ**: 関連する情報源はできるだけ多く使う。同じ内容の重複ページで数を稼いではいけない。募集ページ、FAQ、福利厚生ページ、会社情報、IR、研究所や技術組織のページ、事業・技術説明、口コミ、選考体験など、公式・非公式の両 tier にまたがって多様な種類の情報源を集める。

# 親が渡すデータの読み方
- **固定 scope**: 親が渡す `scope` は、この分析で維持する評価対象である。公開情報とずれて見えても、子が勝手に対象を変更せず、不一致や曖昧さを `scope.ambiguity_note` や section に記録する。
- **近接職種への変更禁止**: 固定 scope が研究職・研究開発職で、当年採用が未定、停止中、終了済み、または情報不足でも、子はデータサイエンス職、SWE、コンサル職などへ置き換えてはいけない。固定 scope のまま、採用導線の弱さや不確実性を記録する。
- **metadata**: `company_name`、`survey_date`、`slug` は出力の識別情報であり、評価対象を広げる根拠ではない。
- **scope.user_label**: ユーザーや親が指定した表示名。
- **scope.target_application_unit**: 応募者が到達したい採用ルート、職種トラック、または application unit。企業名ではない。
- **scope.hiring_entity_name**: 採用を行う entity の名前。給与、採用制度、応募経路の確認ではこの entity を優先する。
- **scope.role_family**: 職種ファミリー。`researcher`、`research_engineer`、`engineer`、`consultant`、`generalist`、`other` のいずれか。採用年度、卒年 cohort、新卒 / 中途区分ではない。
- **scope.alternative_application_units**: `hiring_entity_name` の entity にある他の採用ルート、職種トラック、または application unit。
- **scope.stability_entity_name**: 安定性評価に使う entity の名前。`hiring_entity_name` と違う場合は、その差を保ったまま評価する。

# Scope Gate
- 調査の最初に、親が指定した `scope` が分析可能な応募単位として成立しているか確認する。
- 軽微な曖昧さは `scope.ambiguity_note` に残して分析を続ける。
- 次のような致命的問題がある場合は、通常の company-analysis YAML を作らず、親に scope 修正を依頼する YAML だけを返す。
  - `target_application_unit` が会社名、部署名、研究所名、技術領域名、PR ラベルだけで、応募ルートや職種トラックとして固定できない。
  - `hiring_entity_name` が採用主体として不明、または対象求人・応募ルートと別 entity になっている。
  - `target_application_unit` と `role_family` が明確に矛盾している。
  - 複数の応募単位が 1 target に混ざっており、単一 YAML として評価できない。
  - internship、経験者採用、新卒相当 route が混在し、親がどれを評価したいか判断できない。
- scope 修正依頼 YAML の schema:

```text
scope_check:
  verdict: revise_scope
  slug: <親指定 slug>
  company_name: <親指定 company_name>
  target_application_unit: <親指定 target_application_unit>
  hiring_entity_name: <親指定 hiring_entity_name>
  problems:
    - severity: high | medium
      field: target_application_unit | hiring_entity_name | role_family | alternative_application_units | stability_entity_name | scope
      message: <日本語>
      suggested_fix: <日本語>
  suggested_scope:
    target_application_unit: <候補。分からなければ null>
    hiring_entity_name: <候補。分からなければ null>
    role_family: <候補。分からなければ null>
    alternative_application_units:
      - <候補。候補がなければ空 list []>
    stability_entity_name: <候補。分からなければ null>
```

- `scope_check.verdict: revise_scope` を返す場合も、親指定 handoff path 以外へのファイル作成、保存、Markdown rendering はしない。
- `suggested_scope.alternative_application_units` は list とし、候補がない場合は `[]` を使う。`unknown` や説明文字列で埋めない。
- 子は scope を勝手に修正して分析を続けてはいけない。修正後の scope は親が決める。

## role_family enum
- `researcher`: 研究職、研究員、Research Scientist。研究所や研究職としての入口が主。
- `research_engineer`: R&D職、AI/Data Research Scientist、研究と実装の中間。事業実装に近い研究開発。
- `engineer`: SWE、SE、開発エンジニア、アプリケーションエンジニア、セキュリティエンジニアなど。
- `consultant`: コンサルタント、サイバーコンサル、技術コンサルなど。実装主体ではなく課題解決・支援・変革が主。
- `generalist`: 技術系総合職など、入社時点で研究開発、設計、生産技術、品質、技術営業などに分かれ得るもの。
- `other`: 上記に安全に分類できない応募単位。使う場合は `scope.ambiguity_note` に分類不能な理由を残す。

# Workflow
1. 親が与えた `company_name`、`survey_date`、`slug`、`scope` を、上の読み方に従って確認する。
2. Scope Gate に沿って、親が固定した `target_application_unit` と `hiring_entity_name` が分析可能か確認する。致命的問題があれば `scope_check.verdict: revise_scope` YAML だけを返す。
3. 親が固定した `target_application_unit` が公開情報と整合しているか確認する。
4. 評価対象に関係する公式・非公式の情報源を幅広く集める。
5. 重要な曖昧さや欠損がある点については、公式側・非公式側の両方で追加検索する。
6. 証拠は、まず公式 / 非公式で分け、その中で構造化した事実と叙述的な証拠に整理する。
7. 重要な欠損が残る場合、非公式情報の調査を省略してはいけない。
8. 各評価判断は、整理した証拠に基づいて書き、事実と評価を混ぜない。
9. 採点は、その判断が固まってから付ける。必要ならこの段階で `references/scoring.md` を開く。
10. レポート全体の結論と情報源一覧を完成させる。
11. 各評価判断、採点、結論が固まってから、`references/output-contract.md` や `assets/yaml_output_template.yaml` を開き、最終レポートを整形する。
12. 出力準備中に、裏づけのない主張、未解消の矛盾、追加証拠が必要な重要欠損が見つかったら、確定前に調査へ戻る。
13. 返却前に、構造、型、欠損値の扱いを最終点検する。

# 調査方法
## 情報源の指針
### 公式情報
- **情報源候補**: 採用ページ、募集要項、FAQ、福利厚生・働き方のページ、会社概要ページ、IR / 有価証券報告関連、研究所・技術組織・技術紹介ページ。
- **必須要件**: 最終 YAML の公式 source は 4 件以上とし、採用情報と、会社情報または IR 情報を含める。公開情報が薄く要件を満たせない場合は、不足理由を明示し、validator 失敗や再調査の対象として扱う。
- **優先度**:
  - **共通**: 採用ページ、募集要項、FAQ、福利厚生・働き方のページ、会社概要ページ、IR / 有価証券報告関連を優先する。
  - **研究職寄り**: 研究所・研究活動の説明ページを優先して探す。
  - **エンジニア職寄り**: 技術組織・技術紹介ページ、技術説明ページ、事業と技術の接続が見えるページを優先して探す。
- **注意**: 採用 PR だけに頼ってはいけない。IR、法定開示、研究所ページ、技術論文、事業説明も読み、採用文言と実態を切り分ける。

### 非公式情報
- **情報源候補**: 口コミサイト、選考体験サイト、学生向け就職サイト、個人 blog、個人サイト、CV、研究者 profile、研究室 blog、大学側の再掲募集ページ、イベント告知、発表資料、技術 blog、OSS 活動、GitHub organization などを検索する。典型例として `OpenWork`、`キャリコネ`、`エン カイシャの評判`、`OpenMoney`、`ONE CAREER`、`就活会議`、`外資就活`、`note`、`Qiita`、`Zenn`、`はてなブログ`、`GitHub`、個人サイト / CV、大学・研究室の採用関連ページなどがある。
- **必須要件**: 典型例として挙げた非公式 source は、必ず一度は明示的に検索する。証拠として使わない場合も、確認した source family と不発理由を `facts_unofficial` または `summary.concerns` に残す。
- **優先度**:
  - **共通**: 口コミサイト、選考体験サイト、学生向け就職サイト、個人 blog、個人サイト、CV、研究者 profile、研究室 blog、大学側の再掲募集ページ、イベント告知、発表資料、技術 blog、OSS 活動、GitHub organization などを幅広く当たる。
  - **研究職寄り**: 個人サイト、CV、研究者 profile、研究室 blog、大学側の再掲、open house や event page、研究 internship report を優先してよい。
  - **エンジニア職寄り**: 技術 blog、OSS、GitHub organization、発表資料、ソフトウェア internship report、engineering staff publication を優先してよい。
- **注意**: 非公式情報源は、それぞれが直接支える主張、観測範囲、時期、独立性を記録する。学生向け就職サイトは主に選考理解や職務理解に使うが、初任給候補や募集条件の補助値が見つかる場合は `starting_salary_*` の参考として使ってよい。会社全体の年収を評価対象固有の給与証拠として扱ってはいけない。掲示板や投稿サイトは進み方や不確実性の補助に限る。単発投稿を、それだけで強い証拠として扱ってはいけない。
- **lineage**: 再掲、転載、ミラー、同じサービス内の別ページ、同じ求人票の別掲載面は 1 系統として扱う。独立した支持として数を増やしてはいけない。

## 先に押さえる数値・制度 facts
- **初任給**: 評価対象に最も直接対応する公式の月額初任給。
- **学位別初任給**: 学士・修士・博士の公式月額初任給。
- **採用導線**: 評価対象に対する公式の採用導線と、職種区分そのものの存在。
- **到達経路**: 直接応募、親会社経由、グループ会社経由、または不明という到達経路。
- **平均年収**: 採用主体または公式に正当化できる最も近い範囲の最新公式平均年収。
- **平均残業**: 採用主体または直接関係する従業員集計範囲の公式月平均残業時間。
- **年間休日**: 自分で推定せずに済む明示的な年間休日数。
- **リモート勤務方針**: 制度理解のうえで一貫した分類に落とせる公式のリモート勤務方針。

## 欠損情報
- **共通**: 重要な欠損がある場合は、未確認や非公開と早く確定せず、追加検索を優先する。
- **公式情報**: 公式で埋まらない論点は、対応する非公式情報を重点的に調べ、公開の薄さも残す。
- **非公式情報**: 重要な欠損が残る場合も非公式調査を省略せず、不発理由と関連する観測を残す。
- **補完的推定**: 公式・非公式を探しても直接情報がない場合は、近接職種、同じ採用主体の共通制度、親会社 / グループ制度、業界水準などから留保付きで推定してよい。ただし、推定を構造化 facts として埋めず、section の `evaluation` や `summary.concerns` に根拠の弱さとともに書く。

# 評価基準

## 1. phd_value
- **主判断材料**: 博士向け専用導線、博士の制度上の処遇優位、研究実績の制度上の扱い。学位別初任給差は、博士の処遇優位を示す場合だけ見る。
- **補助材料**: 評価対象に対応する博士応募資格、博士候補を明示的に対象化する採用文言、研究実績を選考で扱う記述。
- **除外**: 面白そうな仕事内容や研究テーマとの相性、給与水準そのもの、研究室規模、R&D テーマの広さ、具体的な初期配属、研究職の存在そのもの、博士保有者の多さ。
- **高評価例**: 博士候補を明示的に対象とし、制度や募集要項で博士向け入口、学位差、研究実績評価、格付け優位のいずれかが確認できる。
- **低評価例**: 公開情報が、博士候補が一般応募者とほぼ同様に扱われること、または博士向け制度 / 評価がほぼ存在しないことを積極的に示している。

## 2. role_fit
- **主判断材料**: 評価対象に対する公式の採用導線、直接到達可否、親会社 / グループ会社経由か、初期配属、職種別採用か総合職か、専門性と仕事内容の接続、配属確度、募集要項の具体性。
- **補助材料**: 選考体験、職種理解、近接職種の情報。
- **除外**: 会社全体の論文数、研究所全体の外部実績、全社的 R&D 投資規模、当年採用の open / undecided / delayed そのもの。必要なら不確実性メモに回す。
- **高評価例**: 初期配属と仕事内容が具体的で、専門性との接続が強く、配属確度も高い。
- **低評価例**: 職務や配属候補が広すぎて、専門性が実務でどう生きるか見えにくい。

## 3. rd_env
- **主判断材料**: 研究所 / R&D 部門、技術発信、論文、特許、会議、OSS、外部連携、理論と実装の往復を支える環境、それらが固定 target に接続する証拠。
- **補助材料**: 全社的な研究投資や技術資産化の情報。ただし固定 target との接続が弱い場合は補助に留める。
- **除外**: 自分の初期配属確度、job title が research っぽいか、特定 1 つのポジションの魅力。
- **高評価例**: 研究所や R&D 部門、論文、特許、会議、OSS、外部連携、技術資産化が複数の手がかりで確認できる。
- **低評価例**: 研究基盤が薄い、外部実績が乏しい、継続的な研究 / 技術アウトプットの支えが弱いという具体的な証拠がある。

## 4. compensation
- **主判断材料**: 評価対象に対応する初任給、平均年収、平均残業時間、年間休日、リモート勤務方針。
- **補助材料**: 賞与、福利厚生、住宅支援、勤務地、働き方。
- **除外**: 学位差の有無や大きさだけで、処遇水準そのものを過大評価しない。学位差そのものの評価は `phd_value` に寄せる。
- **高評価例**: 処遇水準が明確に強い、または評価対象固有の給与が一部非公開でも、柔軟な働き方・福利厚生・低〜中程度の負担が総合して強い。
- **低評価例**: 低い給与、重い残業、低い柔軟性、薄い福利厚生、強い勤務地 / 働き方制約の具体的な証拠がある。

## 5. hiring_process
- **主判断材料**: SPI 等の有無、試験数、online / in person、仙台からの現地面接の負担、研究内容に沿った深掘り。研究深掘りは、generic な就活フィルタや事務負荷とは区別する。
- **補助材料**: 評価対象への到達経路、書類負担、面接回数、選考期間。
- **除外**: 処遇水準そのもの、研究環境の厚み、仕事内容との相性、当年採用の open / undecided / delayed そのもの、仙台から勤務先へ継続的に出社・通勤する想定。必要なら当年採用状況の不確実性として記録する。
- **高評価例**: 採用負担が軽い、面接や試験が少ない / 効率的、online 対応が良い、または研究内容の深掘りを通じて職務適合を確認する納得感がある。
- **低評価例**: generic な就活フィルタが強い、SPI 等に加えて面接や提出物が多い、全体負担が高い。

## 6. stability
- **主判断材料**: 固定された `stability_entity_name` に対応する会社情報、IR、法定開示、売上、従業員数、資本金、上場有無、親 / グループ支援、事業継続性。
- **補助材料**: 会社評判、事業見通しに関する追加情報。
- **除外**: 評価対象への到達経路や研究職への配属経路は補助情報としてのみ使う。
- **高評価例**: 売上規模や従業員規模が大きく、上場企業または大手親会社 / グループの支援があり、継続的な事業運営を支える会社情報や IR が複数確認できる。
- **低評価例**: 継続赤字、大きな事業縮小、人員削減、親 / グループ支援の弱さなど、雇用や組織継続への不安を示す具体的な証拠がある。
