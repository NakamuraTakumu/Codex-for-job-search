# When to use
- このスキルは、会社分析を取り回す親エージェントが使うことを前提とする
- 企業が、旧帝大の博士課程人材にとって就職先として有力かを評価したいとき
- 研究開発職、技術職、専門職、研究所採用、R&D 採用などを比較したいとき
- 一般的な企業紹介ではなく、博士人材としての適合性を見たいとき
- SPI などの一般適性検査を含む選考負担も評価に入れたいとき
- 複数企業を同じ基準で比較できる形で Markdown に保存したいとき

# Default assumptions
- 志望者は旧帝大の博士課程人材である
- 関心領域は以下を既定値とする
  - 機械学習
  - 数理・抽象理論
- 圏論・形式化
- 学習アルゴリズムのモジュール化・構成法・性質分析
- プログラミング言語理論
- ソフトウェア工学
- アルゴリズム実装
- GPU / 型システムなどの計算機実装
- 研究成果のソフトウェア化・社会実装
- 親エージェントが委譲前に `評価対象`、`採用主体`、`採用職種` を固定する
- このスキルは、親エージェントが固定した `評価対象` を前提に評価する
- `採用主体`、`評価対象`、`採用職種`、`主な配属候補` がずれる場合は、それぞれ分けて明記する
- 売上高、従業員数、資本金など企業基盤の数字にグループ全体や親会社を使う場合は、採用単位とのずれを明記する
- 分野適合による上振れは行わない
- 不明な情報は推測で埋めず、`不明` と書く

# Core principles
- 企業の宣伝文句を要約せず、就職先としての実態を評価する
- 事実と評価を分ける
- 可能な限り公式情報を優先する
- 同じ内容を複数項目で二重計上しない
- 大手感、雰囲気、ブランドイメージでは加点しない
- 研究能力と関係の薄い選考負担が重い企業は明確に減点対象とする
- 回答だけで終えず、最終結果を Markdown ファイルとして保存する

# Scope resolution
- 原則として、`評価対象` の確定は親エージェントが行う
- このスキルは、固定された `評価対象` と `採用職種` を前提に評価を進める
- 出力する Markdown では、固定した `評価対象` を `分析対象単位` 欄に記載する
- 固定された `評価対象` が公開情報とずれている、存在しない、または曖昧すぎると分かった場合でも、子エージェント側で勝手に別の対象へ切り替えない
- その場合は、不整合または曖昧性として明記し、必要なら親エージェントが再解決すべき点として報告する
- `評価対象` や `採用職種` に曖昧性が残る場合は、その曖昧性を明記し、暫定評価であることを書く

# Evaluation criteria

## 1. 博士人材の評価
見る点:
- 博士採用枠の有無
- 学士・修士・博士で初任給テーブルが分かれているか
- 博士向け職種や期待役割があるか
- 博士出身者の採用実績や活躍事例があるか
- 博士号そのものではなく、専門性が評価される設計か

## 2. 仕事内容・配属確度
見る点:
- 初期配属がどの職種・部門に近いか
- ジョブ型か、総合職一括か
- 研究テーマや専門性との接続が明確か
- 配属確約、職種別採用、研究所別採用の有無
- 実際に何を作る・何を研究する・何を運用するのかが具体的か

## 3. 研究開発・技術環境
見る点:
- 研究所や R&D 部門の有無
- 論文、特許、学会発表、OSS、技術発信
- 基礎研究寄りか、応用研究・実装寄りか
- 研究成果が実装や事業に接続されているか
- 理論と実装を往復できる環境か

## 4. 処遇・働き方
見る点:
- 初任給
- 学位ごとの給与差
- 賞与
- 福利厚生
- 住宅補助
- 勤務地
- 働き方  （フレックス、在宅、残業など）
- 裁量や自由度がどれくらいあるか

## 5. 選考コストと評価の納得感
見る点:
- SPI、玉手箱、TG-WEB、CAB、GAB などの有無
- Web テストが複数あるか
- ES の分量が過大か
- 面接回数が多すぎないか
- 研究内容、実装経験、論文、発表、GitHub などを直接見てくれるか
- generic な足切り中心か、専門性評価中心か

高評価:
- 選考負担が軽い
- 研究能力や専門性を直接評価する
- 準備コストに対して評価の納得感が高い

低評価:
- SPI などの一般適性検査が重い
- 就活慣れを強く要求する
- 専門性と無関係な負担が大きい

## 6. 企業基盤・安定性
見る点:
- 売上高
- 従業員数
- 資本金
- 上場の有無
- 親会社やグループ基盤
- 事業継続性

注意:
- 主軸ではなく補助項目として扱う

# Scoring
各項目を 5 点満点で採点し、次の式で 100 点満点に換算する。
- 各項目スコアは `0.1` 刻みで付ける
- `0.5` 刻みへ丸めてから記入しない
- 各項目スコアは `1.0` 以上 `5.0` 以下とする

    総合評価 = 20 × (
    0.30×博士人材の評価
    + 0.10×仕事内容・配属確度
    + 0.05×研究開発・技術環境
    + 0.25×処遇・働き方
    + 0.10×選考コストと評価の納得感
    + 0.20×企業基盤・安定性
    )

# Score display rules
- `数式評価` では、6項目の点数、計算式、計算結果を省略せずに書く
- `数式評価` の最終値は小数第1位まで表示する
- `最終評価` は `数式評価` の最終値をそのまま再掲する
- `80.5` を `81` のように丸めて再表示しない
- 各項目の `スコア` は `4.0 / 5.0` のように小数第1位までそろえて書く

# Output contract
- 出力は Required output structure の見出し順を必ず守る
- 見出し名は省略・言い換え・並び替えをしない
- `# {企業名}` の直下に、空行を入れず `調査日: YYYY-MM-DD` を置く
- `調査日` を `## 結論` の中や箇条書きの中に入れない
- 各評価節は必ず `- 事実:` `- 評価:` `- スコア:` の3行を含む
- `不明` な情報は推測で補わず、そのまま `不明` と書く

# Adjustment rule
- 原則として補正は行わない
- 補正を行ってよいのは、各評価項目の中にきれいに含められないが、総合判断では無視できない事情がある場合に限る
- 補正は、各項目で既に採点した内容の言い換えや再計上には使わない
- 分野適合、大手感、雰囲気、直感には使わない
- 補正を使う場合は最大 ±5 点までとし、理由を 1 文で明示する

補正に使ってよい例:
- 公開情報が少なすぎて、総合評価全体の信頼性が低い
- 情報が古く、現状を反映しているか不安がある
- 会社全体の評価と、実際に応募する採用枠・配属先の単位が大きくずれている
- グループ全体の数字は大きいが、応募先単体の実態とは乖離している
- 公開フローは重いが、博士向けには別ルートが確認できる

補正に使ってはいけない例:
- SPI があるから下げる
- 博士給与が不明だから下げる
- 研究所があるから上げる
- 大企業だから上げる
- 分野的に合いそうだから上げる

# Workflow
1. ユーザー指定名を確認する
2. 親エージェントが固定した `評価対象`、`採用主体`、`採用職種`、`主な配属候補` を確認する
3. 企業の基本情報を確認する
4. 採用ページと職種情報を確認し、固定された `評価対象` が公開情報と整合するかを確認する。整合しない場合は別対象へ切り替えず、不整合として記録する
5. 博士人材の扱いが明示されているか確認する
6. 仕事内容と配属の具体性を確認する
7. 研究開発・技術環境の実在性と規模を確認する
8. 初任給、福利厚生、働き方を確認する
9. 選考フローを確認し、選考コストを評価する
10. 企業基盤・安定性を確認する
11. 事実と評価を分けて整理する
12. 数式評価を算出する
13. 補正が必要かを検討する
14. 別エージェントに、各項目スコアと総合評価が `事実` と `評価` に照らして妥当かを独立に検査させる。別エージェントを使えない場合は、独立した再計算と逆方向の批判的レビューで同等の検査を行う
15. 別エージェントの指摘、または独立検査で見つかった不整合を確認し、必要なら点数または評価文を修正する。自己レビューでは代替しない
16. 保存前に Required output structure と score display rules を満たしているか自己点検する
17. 最終結果を Markdown ファイルとして保存する
18. 回答では、要約と保存ファイルへの参照を返す

# Pre-save checklist
- `# {企業名}` の直下に `調査日: YYYY-MM-DD` がある
- `## 分析対象の確定` がある
- 6つの評価項目すべてに `- 事実:`、`- 評価:`、`- スコア:` がある
- `数式評価` の最終値と `最終評価` の数値が一致している
- 別エージェントによる採点妥当性の検査、または同等の独立検査を実施し、重大な不整合を放置していない。自己レビューのみで済ませていない
- `不明` な情報を推測で埋めていない
- 事実と評価が混ざりすぎていない
- 保存前に必要なら `python3 tool/check_company_analysis.py <output-file>` で形式検査してよい

# Allowed variation
- `事実` と `評価` の本文量は企業ごとに変えてよい
- `結論`、`向いている人`、`向いていない人`、`懸念点` は箇条書きでも段落でもよい
- ただし、必須見出し、`調査日` の位置、`事実 / 評価 / スコア`、数値表示規則は固定する

# Saving rule
- 最終結果は必ず Markdown ファイルとして保存する
- 保存先は原則として workspace の `document/company_analysis/companies/` ディレクトリとする
- ファイル名は `<company_name_slug>.md` とする
- `company_name_slug` は、固定した `評価対象` を英小文字の ASCII に正規化して作る
- 空白は `_` にする
- `&`、`/`、`-` などの区切り記号は原則 `_` に統一する
- 連続する `_` は 1 つに潰す
- 日本語社名で自然な英字 slug がある場合はそれを使い、ない場合は一般に通用するローマ字または英訳を使う
- 同じ企業名でも `評価対象` が違う場合は slug を分ける
- 回答時には、保存した Markdown ファイルへの参照も返す
- 参考文献は、可能な限り公式情報を優先する
- URL または出典名を列挙する
- 不明な情報は `不明` と書く

# Response style
- 冗長な企業紹介にしない
- 事実と評価を明確に分ける
- 結論を先に書く
- 推測は推測と明記する
- 総合評価の算出過程を省略しない
- 数式評価、補正、最終評価を分ける
- 選考負担については曖昧にせず、明確に評価する
